--------------------------------------------------------------------------------
1. MODULE OVERVIEW
--------------------------------------------------------------------------------
Purpose:
- Record sales orders: which customer bought which products, in what quantities,
  at what price, and the order's lifecycle status. Each order has one or more
  line items and a computed total.

Business objectives:
- Capture revenue-generating transactions accurately.
- Preserve historical pricing (snapshot unit price at order time).
- Track fulfillment via an order status lifecycle.
- Feed the Dashboard and Reports modules with revenue data.

--------------------------------------------------------------------------------
3. DATABASE
--------------------------------------------------------------------------------
New table: orders
- id            UUID PK DEFAULT gen_random_uuid()
- order_number  VARCHAR(30) NOT NULL UNIQUE       -- human-friendly, e.g. ORD-000123
- customer_id   UUID NOT NULL REFERENCES customers(id) ON DELETE RESTRICT
- status        VARCHAR(20) NOT NULL DEFAULT 'draft'
                -- draft|confirmed|paid|shipped|completed|cancelled
- currency      VARCHAR(3)  NOT NULL DEFAULT 'USD'
- subtotal      NUMERIC(12,2) NOT NULL DEFAULT 0  -- sum of line totals (computed)
- total         NUMERIC(12,2) NOT NULL DEFAULT 0  -- subtotal (+ future tax/discount)
- notes         TEXT NULL
- created_by    UUID NULL REFERENCES users(id) ON DELETE SET NULL
- created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
- updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()

New table: order_items
- id            UUID PK DEFAULT gen_random_uuid()
- order_id      UUID NOT NULL REFERENCES orders(id) ON DELETE CASCADE
- product_id    UUID NOT NULL REFERENCES products(id) ON DELETE RESTRICT
- product_name  VARCHAR(255) NOT NULL   -- snapshot of product name at order time
- unit_price    NUMERIC(12,2) NOT NULL  -- snapshot of product price at order time
- quantity      INTEGER NOT NULL        -- > 0
- line_total    NUMERIC(12,2) NOT NULL  -- unit_price * quantity
- created_at    TIMESTAMPTZ NOT NULL DEFAULT now()

Relationships:
- orders.customer_id -> customers.id (RESTRICT: cannot delete a customer with orders)
- orders.created_by  -> users.id
- order_items.order_id -> orders.id (CASCADE: deleting an order deletes its items)
- order_items.product_id -> products.id (RESTRICT: cannot delete a product in use)

Constraints:
- order_number UNIQUE + NOT NULL (generated by service; see §6).
- status in the allowed set (CHECK + service validation).
- quantity > 0; unit_price >= 0; line_total = unit_price * quantity.
- subtotal/total NUMERIC(12,2) recomputed from items on every mutation.

Indexes:
- ux_orders_order_number UNIQUE on orders(order_number)
- ix_orders_customer_id  on orders(customer_id)
- ix_orders_status       on orders(status)
- ix_orders_created_at   on orders(created_at)
- ix_order_items_order_id on order_items(order_id)
- ix_order_items_product_id on order_items(product_id)

Provide idempotent, Supabase-safe sql/orders.sql for both tables.

--------------------------------------------------------------------------------
4. BACKEND
--------------------------------------------------------------------------------
SQLAlchemy models: Order (with `items` relationship, cascade delete-orphan) and
OrderItem. Decimal for all money fields.

Pydantic schemas:
- OrderItemCreate -> product_id (UUID), quantity (>0)
- OrderCreate     -> customer_id (UUID), notes?, items (>=1 OrderItemCreate)
- OrderUpdate     -> notes?, items? (full replacement of lines; only when status
                     allows editing — see §6)
- OrderStatusUpdate -> status (enum)
- OrderItemOut    -> id, product_id, product_name, unit_price, quantity, line_total
- OrderListItem   -> id, order_number, customer summary, status, total, currency,
                     created_at, item_count
- OrderDetail     -> header fields + customer summary + items[] + created_by
- Paginated[OrderListItem]

Repository (orders_repository.py):
- list_orders(db, *, search, status, customer_id, date_from, date_to,
              sort, order, page, page_size) -> (rows, total)
- get_order(db, id) (eager-load items + customer)
- create_order / replace_items / update_status / delete_order
- next_order_number(db)  (sequence-based; see §6)

Service (orders_service.py) — raises ValueError; wrap multi-row writes in ONE
transaction:
- create_order(db, actor, data):
    * validate customer exists,
    * validate each product exists AND is_active,
    * snapshot product_name + unit_price from products,
    * quantity>0; check stock_qty >= quantity; decrement stock,
    * compute line_total, subtotal, total,
    * generate order_number, set created_by, status='draft'.
- update_order_lines(db, id, data): only if status in editable set; restock old
  items, re-apply new items (re-validate stock), recompute totals.
- change_status(db, id, new_status): enforce allowed transitions (§6); on
  'cancelled' restock items.
- delete_order(db, id): only drafts/cancelled (§6); restock if needed.

Routers (routers/orders.py, /api/orders): thin, permission-guarded, map
ValueError -> 400/404/409.

Validation: customer/product existence; product active; quantity>0; stock
sufficiency; valid status transitions.

Error handling: 401/403/404; 409 (insufficient stock, illegal status
transition, delete not allowed); 400 business rule; 422 schema.

5. REST APIs
--------------------------------------------------------------------------------
(1) List orders
    URL: GET /api/orders
    Query: search (order_number|customer name), status, customer_id,
           date_from, date_to, sort (created_at|total|order_number|status),
           order, page, page_size
    Response: Paginated[OrderListItem]
    Permission: orders.read

(2) Get order
    URL: GET /api/orders/{id}
    Response: OrderDetail (with line items)
    Permission: orders.read

(3) Create order
    URL: POST /api/orders
    Body: OrderCreate
    Response: OrderDetail (201)
    Permission: orders.create

(4) Update order (lines / notes)
    URL: PATCH /api/orders/{id}
    Body: OrderUpdate
    Response: OrderDetail
    Permission: orders.update

(5) Change status
    URL: POST /api/orders/{id}/status
    Body: OrderStatusUpdate
    Response: OrderDetail
    Permission: orders.update

(6) Delete order
    URL: DELETE /api/orders/{id}
    Response: 204 (only draft/cancelled)
    Permission: orders.delete

6. BUSINESS RULES
--------------------------------------------------------------------------------
- order_number is unique and generated server-side (e.g. 'ORD-' + zero-padded
  value from a Postgres sequence). Never client-supplied.
- An order must have at least one line item; each quantity > 0.
- Line prices are SNAPSHOTS: product_name and unit_price are copied from the
  product at creation and never change if the catalog changes later.
- Only is_active products can be added to new/edited orders.
- Stock: creating/expanding an order decrements product stock_qty and must not
  drive it below 0 (409 insufficient stock). Cancelling or deleting restocks.
- Totals: subtotal = sum(line_total); total = subtotal (tax/discount are future
  extensions). Totals are always recomputed server-side, never trusted from the
  client.
- Status lifecycle (allowed forward transitions):
    draft -> confirmed -> paid -> shipped -> completed
    (any non-terminal) -> cancelled
  Illegal jumps (e.g. draft -> shipped, or changing a completed/cancelled order)
  are rejected (409).
- Editing lines/notes is allowed only while status is 'draft' (and optionally
  'confirmed'); paid/shipped/completed orders are immutable except via status.
- Deletion allowed only for 'draft' or 'cancelled' orders; others must be
  cancelled first (preserves financial history).
- Deleting an order cascades its order_items (DB), but products/customers remain.
- A customer or product referenced by any order cannot be hard-deleted (RESTRICT
  in DB; surfaced as 409 by those modules).
- All monetary math uses Decimal / NUMERIC(12,2).

8. FRONTEND
--------------------------------------------------------------------------------
Jinja2 shells + vanilla JS + Bearer token (auth.js pattern). Optional CNN tokens.

List page (/orders): table Order #, Customer, Status badge, Items, Total
(formatted), Created. Row actions View/Edit/Delete. "New order" gated by
orders.create. Status badges color-coded.

Create page (/orders/new): pick customer (searchable dropdown), add line items
(product picker limited to active products, quantity input), live client-side
subtotal/total preview (server remains source of truth). Submit creates a draft.

Edit page (/orders/{id}/edit): editable only for draft (and confirmed) orders;
add/remove/change lines and notes; disabled with an explanation for locked
statuses.

Detail page (/orders/{id}): header (customer, status, totals), line-items table,
and a status-change control offering only legal next statuses. Cancel action
where allowed.

Search: order_number OR customer name.

Filters: status, customer, date range (date_from/date_to).

Pagination: page + page_size (default 20) with totals.

Sorting: created_at, total, order_number, status.

Responsive: line-items table scrolls/stacks on mobile; sticky total on small
screens.

Validation: require a customer and >=1 line; quantity>0; block submit if a
picked product is inactive or out of stock; surface API 409 (insufficient stock,
illegal transition) clearly.
