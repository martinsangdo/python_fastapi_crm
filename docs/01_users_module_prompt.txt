ROLE
You are a senior FastAPI engineer extending an existing, beginner-oriented CRM
scaffold. Match the codebase's existing style: layered architecture, UUID
primary keys, timezone-aware timestamps, thin routers that translate service
ValueErrors into HTTP responses, and verbose, explanatory comments aimed at a
learning audience. Do NOT redesign existing tables. Reuse the existing auth
building blocks (security.py, dependencies.py, auth_service.py, models.py).

--------------------------------------------------------------------------------
1. MODULE OVERVIEW
--------------------------------------------------------------------------------
Purpose:
- Provide administrators a full management surface for the people who can log in
  to the CRM (the `users` table) and the roles they are assigned.
- This module turns the existing authentication + RBAC data into a usable admin
  screen: create users, deactivate them, reset roles, and browse who has access.

Business objectives:
- Give Admins control over who can access the CRM and at what permission level.
- Enforce least privilege by attaching exactly one role per user.
- Keep an auditable, filterable list of accounts (active/inactive, by role).
- Never expose password hashes; never allow privilege escalation by non-admins.

    * raise HTTP 403 if the required `code` is not present,
    * return the current user on success.
  Usage in routers: `user = Depends(require_permission("users.read"))`.
- Add a helper `get_user_permission_codes(db, user) -> set[str]` in the service
  or authorization layer.

--------------------------------------------------------------------------------
5. REST APIs
--------------------------------------------------------------------------------
(1) List users
    URL: GET /api/users
    Query: search, role_id, is_active, sort (created_at|email|full_name|last_login),
           order (asc|desc), page, page_size
    Description: Paginated, filterable, sortable list.
    Response: Paginated[UserListItem]
    Permission: users.read

(2) Get user detail
    URL: GET /api/users/{user_id}
    Response: UserAdminDetail (includes role + effective permission codes)
    Permission: users.read

(3) Create user
    URL: POST /api/users
    Body: UserAdminCreate
    Response: UserAdminDetail (201)
    Permission: users.create

(4) Update user
    URL: PATCH /api/users/{user_id}
    Body: UserAdminUpdate
    Response: UserAdminDetail
    Permission: users.update

(5) Reset password
    URL: POST /api/users/{user_id}/reset-password
    Body: UserAdminPasswordReset
    Response: { "detail": "Password reset." }
    Permission: users.update

(6) Activate / Deactivate
    URL: POST /api/users/{user_id}/activate  and  /deactivate
    Response: UserAdminDetail
    Permission: users.update

(7) Delete user
    URL: DELETE /api/users/{user_id}
    Response: 204 No Content (or 200 with detail)
    Permission: users.delete

(8) List roles (for dropdowns)
    URL: GET /api/roles
    Response: list[RoleSummary]
    Permission: users.read

6. BUSINESS RULES
--------------------------------------------------------------------------------
- Exactly one role per user (role_id nullable; a user may temporarily have none).
- Email is unique and case-insensitive; store normalized lowercase.
- Passwords are stored only as bcrypt hashes via hash_password(); plain text is
  never stored, logged, or returned.
- Self-protection: a user cannot deactivate or delete their own account.
- Last-admin protection: the system must always retain at least one ACTIVE user
  with the ADMIN role. Block deactivation/deletion/role-change that would remove
  the final active admin (raise ValueError -> 400).
- Deactivation vs deletion: prefer deactivation (is_active=False) for audit
  history; deletion is a hard delete and requires users.delete. Deleting a user
  does NOT delete their role.
- Deactivated users cannot log in (already enforced in get_current_user).
- Only users with users.update may change another user's role (no self role
  escalation via this module).
- Detail response exposes effective permissions (role -> permissions) read-only;
  editing permissions/roles-to-permissions is out of scope for this module.

- users.read    — view user list and detail, list roles
- users.create  — create users
- users.update  — edit users, reset password, activate/deactivate, set role

8. FRONTEND
--------------------------------------------------------------------------------
Stack: Jinja2 server-rendered shells + plain HTML/CSS + vanilla JS that calls the
JSON API with the Bearer token (follow the existing static/auth.js pattern:
token stored client-side, redirect to /login when missing/expired). Optionally
follow the CNN design system tokens (near-black ink on white, red reserved for
accents, 8px grid, square blocks).

List page (/admin/users):
- Table columns: Full name, Email, Role, Status (Active/Inactive badge),
  Last login, Created. Row actions: View, Edit, Activate/Deactivate, Delete.
- "New user" button (visible only if users.create in the current user's perms).

Create page (/admin/users/new):
- Fields: full_name, email, password, role (dropdown from GET /api/roles),
  is_active toggle. Client + server validation.

Edit page (/admin/users/{id}/edit):
- Edit full_name, role, is_active. Separate "Reset password" action.
- Email shown read-only (changing login email is out of scope).

Detail page (/admin/users/{id}):
- Read-only profile: identity, role, effective permissions list, timestamps,
  last login. Action buttons gated by the viewer's permissions.

Search: single search box matching email OR full_name (case-insensitive, partial).

Filters: role (dropdown), status (all/active/inactive).

Pagination: page + page_size (default 20), show total and page controls.

Sorting: clickable headers for full_name, email, last_login, created_at (asc/desc).

Responsive layout: table collapses to stacked cards on small screens; actions in
an overflow menu on mobile.

Validation: inline field errors, disable submit while pending, surface API 4xx
messages (duplicate email, last-admin rule) near the relevant field or as a banner.

UI permission-gating: hide/disable create/edit/delete controls when the logged-in
user lacks the matching permission (defense in depth — server still enforces).
